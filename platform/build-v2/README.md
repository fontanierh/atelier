# Build v2 interfaces (A0)

This unused Rust library is the shared interface for the build-v2 tracks. Production v1 is unchanged.
Declaration schema **2** (fixed declarations v1 remain readable), result schema **3** and protocol
version **1** are the wire contracts; incompatible changes
require a version bump and coordination with consumers. The lockfile pins this crate's dependencies,
not game cache identities.

- `schema`: `Declaration`, `Unit`, `Input`, `Item`, `ResultRecord`, `IdentityIngredients`.
- `protocol`: `JobRequest`, `Request`, `Response`, `read_frame`, `write_frame`.
- `fixture`: `Worker`, `MockWorker`, `MockStep`, `FixtureFile`.
- `explain`: observational `Recorder`, compact ingredient differences and per-unit `BuildSummary`;
  see [summary semantics](../../docs/build-v2/EXPLAIN.md). CLI wiring remains I2.

[examples/units.toml](examples/units.toml) is a complete parseable declaration. Code lists are explicit,
project-relative and include the entry script. Loading undeclared project code will be refused by the
later worker adapter. A selector is an RFC 6901 JSON pointer. References identify logical path and class,
name their proof test and optionally link a producer item for scheduling; producer bytes are not reference
identity. Content inputs link a file/selector or a producer unit/item. File sources explicitly mark optional inputs; `ContentIdentity::Absent` differs from any digest, including
an empty file. Item `files` is the complete permitted set: each `OutputFile.path` is job-output-relative,
`install_path` is checkout-relative, and `required` defaults to true. Optional native sidecars set it false;
`StoredItem.files` records the exact emitted set. A2 validates required outputs and install ownership. External outputs allow a later Zen adapter to name its locator.

These are **unvalidated data types**. A2 adds semantic validation (versions, paths, closure, graph,
ownership, op registry); A3 computes keys. Digests are opaque strings here. `ResultRecord.key` is the
producing input key; each `StoredFile.digest` is that exact file's content digest. Worker and validator
versions and digests are explicit identity fields. Checkout/branch/commit/dirty/time live only in provenance.

Frames are a four-byte unsigned big-endian byte count followed by UTF-8 JSON, at most 8 MiB:

```json
{"version":1,"message":{"type":"shutdown"}}
```

Requests: `run` (one `job`), `cancel` (`job_id`), `shutdown`. Responses: `hello` (`worker_version`),
`started` (`job_id`), `completed` (`job_id`, `outputs.files`), `failed` (`job_id`, `failure.kind`,
`failure.message`), `stopped`. Protocol JSON carries paths and metadata, never asset bytes. Run jobs
name a staged `job_dir`, relative script/code/input paths, parameters and allowed outputs (with required/optional status) under
`output/`. Logs use stdout/stderr, never the protocol pipe. C1 owns session ordering and staging;
C5 owns retries, deadlines and guard-stop policy. A0 never interprets a returned path as validated.

`MockWorker::new` takes ordered `MockStep`s. `Worker::run` records each request, returns scripted
paths/failures and keeps generated bytes in `produced()` for the harness. Unknown or out-of-order
jobs fail. A step can return any failure class or arbitrary files (including a plan payload). More
elaborate hooks and pending/crash processes belong to A8; this mock does no filesystem or native work.

Local compile/tests must use the standalone compile admission described in
[BUILD_CAPACITY](../../docs/BUILD_CAPACITY.md#standalone-native-tool-builds), with three workers.
Run from this crate directory so `.cargo/config.toml` places generated files in `build/build-v2/`:
`cargo test --locked`. Compilation time and test execution time are reported separately.

## Host CI tiers (A1, H5b)

Every PR runs the `Rust / host tiers` hosted job. It compiles the current crate with three workers,
then runs pinned cargo-nextest 0.9.149 twice, in two required steps of the same job: profile `ci`
for T0 with a ten-second global test timeout, and profile `t1a` for tests that execute a real
Python op or job with a thirty-second one. Both keep three test threads, no retries and no ignored
tests. Compile time is reported in its own step. The job retains the full collection, each tier's
filtered listing, both JUnit execution/timing artifacts and the derived filter plan; neither a
cached binary nor an empty test run can provide success.

`tests/registry/<task>.toml` holds one fragment per task, each with `schema_version = 1` and its
`scenarios` and `pending` rows. The loader discovers the fragments from the explicit directory,
merges them in filename order and refuses any other directory entry, unknown key, malformed row or
empty fragment. Active rows map each scenario to nextest IDs (`binary-id/test-name`). The hook
checks that collection and execution cover exactly those tests once, with no ignored, filtered,
skipped, failing or unmapped tests.

Each active row declares `tier`: `t0` for wire, schema, key, filesystem and process-mechanism
decisions, `t1a` for tests that execute a real Python op or job, `t1b` for real Blender and `t2`
for real Unreal. The checker derives one nextest filter expression per host tier from that field,
so a test that shares a binary with tests of another tier is selected by its own test ID. `t1b`
and `t2` never run in either host step; they are reported as explicit native exclusions and never
count as coverage. A missing or unknown tier fails the check.

Add an active row to your task's fragment with each new T0 scenario; use the named scenario IDs in
future engine tests. Future required scenarios remain explicit `pending` rows in the fragment of
the task that will implement them. A pending row is a gap, not a pass. A8/H5 will activate those
rows as the engine/reference model is implemented; A1 does not claim the full TESTING scenario
suite exists.

The registry checker is a read-only Python tool. Its focused tests run in ordinary Python CI:
`uv run pytest platform/studio/tests/test_build_v2_registry.py -q`. A local nextest compile/run must
still use the standalone admitted compile workflow; the CI profile is not a memory/admission guard.

## Declaration validation (A2)

`validate::load` parses TOML and checks it against caller-supplied `OpRegistry`, `SourceSnapshot` and
allowed checkout install roots. `validate::validate` checks an already parsed declaration. The registry
names supported op/version pairs, their named input roles/requiredness, optional-file/selector policy,
accepted input-item classes, output classes and named parameter types/requiredness. Missing definitions,
unknown names and invalid top-level parameter types fail; nested domain constraints belong to each op.

The snapshot is an immutable map of exact project-relative file names to frozen bytes or an explicit
non-regular/unreadable state. Absence is a missing entry; it is permitted only for an explicitly optional
file accepted by the op. Missing JSON selector nodes always fail when the file exists, including when
that file is optional. Successful validation returns dependency order and resolved whole/absent/selected
file observations. It does not hash inputs, discover imports, walk the live checkout, stage files, launch
workers or decide cache hits. The snapshot provider must include the real ignored/untracked inputs and
establish physical path provenance; later A3/C1/A6 bind bytes, enforce loaded code and check mid-build edits.

Paths must be relative, with no empty/dot/traversal components, backslashes, drive colons, controls or
trailing dot/space aliases. Logical output/reference paths start with `/`. Source Unicode names retain
exact spelling. Owned-path collision comparison uses canonical Unicode decomposition and full non-Turkic
case folding, then decomposition again; it rejects equal and ancestor/descendant ownership, including
optional sidecars. This is a conservative portable collision policy, not an emulator of every APFS
Unicode revision. Representative ASCII case and composed/decomposed aliases and ancestor conflicts were
also checked with exclusive file creation on the local case-insensitive filesystem. Full physical-path
and native receiving acceptance remains a pre-cutover responsibility; validation alone makes no claim
about symlink aliases outside the supplied snapshot or every filesystem's Unicode rules.

Job-output names are scoped to one unit's scratch output; checkout install ownership is global across
the declaration and must stay under the caller's allowed roots. Raw/store paths may therefore match a
finish unit's logical asset identity without sharing mutable outputs. Checkout logical owners are
unique. Neither code nor declared file inputs may overlap checkout installs. A unit's entry script must
be listed in its explicit code closure, but the validator does not pretend that this proves all dynamic
imports are declared. Content and linked-reference producers must exist; linked references must agree
on logical path/class and carry a proof-test name. Broad/aggregate op slots marked
`require_whole_reason` require a nonempty rationale; already bounded payloads, FBX or narrow query
results need no boilerplate note. The op definition and recipe review establish that classification.
Producer scheduling cycles fail.

Focused cases in `tests/validation.rs` cover absence, selectors, missing or non-regular inputs, op rules,
producer identity, cycles, invalid paths, Unicode collisions, disjoint output ownership and install roots.
The library remains unused by production v1. Its tests run in hosted Rust CI; local compilation still
requires ordinary standalone compile admission.

## Immutable objects (B1)

`store::ObjectStore::open(root)` uses an explicit trusted store root. Object format **1** stores
payloads at `objects/sha256/<64 lowercase hex characters>`. It has no default machine path and no
production callers. Changing algorithm or encoding requires a new format/namespace.

`prepare(source)` clones a regular source into a newly reserved private staging directory, freezes
the snapshot read-only, hashes its exact bytes once and returns a private `PreparedObject` token.
`publish(token)` accepts only a token from the same store and publishes with macOS `RENAME_EXCL`.
The first entry wins; an existing regular read-only entry is kept, with a cheap size check. Existing
object contents are trusted on ordinary hits; B7 owns explicit corruption verification and recovery.
A dropped/failed token cleans only its own staging payload and empty private directory. Source files
remain unchanged. This is not a result transaction: B2 must lease before calling prepare and retain
that lease through its publication/record lifecycle. No cleanup, root or result-record engine exists here.

`clone_to(digest, destination)` uses APFS `clonefile`, never rehashes or scans, refuses an existing
destination and never copies bytes as a fallback. Unsupported platforms/filesystems and other clone
errors are explicit failures. The cloned payload is read-only; B2/B3 must retain/install source modes
from the publication receipt (including executable permissions) as result metadata. B1 stores bytes,
not checkout install policy or file-mode identity.

The Rust job now runs on Linux and macOS. Registry `platforms` may contain only `linux`/`darwin`;
selection uses the host triple recorded in nextest's listing, so downloaded evidence is interpreted
independently of the reviewer's machine. Excluded-platform scenarios are reported separately, never
counted as passes. Linux tests prove explicit unsupported behavior; mandatory macOS tests prove real
APFS cloning, independent edits, read-only snapshots, no-replace races and owned cleanup. Both jobs
keep compile time separate from the ten-second T0 run. Local native repetition is reserved for a
specific CI coverage gap or diagnosis, through the ordinary admitted compile workflow.

## Unit keys and source hash hints (A3)

`keys::prepare` consumes an A2-validated declaration, the same frozen source snapshot, explicit
worker/validator code identities, current produced-item manifests and a complete staged-slot map.
It returns an immutable `PreparedUnit`: the SHA-256 key, typed ingredients, input staging payloads
and a `JobRequest` template. The library remains unused by production builds.

Keys use a domain/version-tagged canonical JSON encoding: recursively sorted object keys, sorted
code/output memberships and exact primitive/array data. Ingredients include cache/op versions,
selected entry script plus declared project-code hashes, worker/validator versions and code hashes,
semantic parameters, logical output identities, content identities, references and staged paths.
Installed Python/libraries/lockfiles, Blender/add-ons, Unreal and compiler/SDK versions are not
implicitly discovered or hashed. Platform invalidation requires explicit op/cache version changes.
Project-owned settings/code remain declared inputs. Provenance and stat hints are outside identity.

A content dependency consumes the exact saved file manifest: relative member names, byte SHA-256,
size and normalized semantic mode. It never consumes the producer's input key, source closure or
capture provenance. Missing required members fail. External/Zen items need their future typed adapter;
this API refuses to invent their content identity. References bind only logical path/class; their
staged descriptor contains exactly those fields, never referenced asset bytes.

Raw files stage exact bytes. JSON selectors stage canonical bytes of the selected value with its
actual shape, without source locator or selector text. Optional absence is an explicit absent identity,
not an empty file, JSON null or missing node. Missing selector nodes still fail validation. A source
locator/selector rename that preserves this staged view leaves the key unchanged.

**Worker-visible staging contract:** every declared slot has one explicit safe relative path. Raw,
selected and reference-descriptor inputs use that file name (including extension); multi-file items
use a directory root with their exact recorded member names. Equal/casefold/normalization/ancestor
collisions fail across staged slots, project code and the reserved writable `output/` tree.
Code retains its declared relative paths; neither code nor inputs may occupy `output/`. The same
conservative normalized path policy is shared with A2. This full map enters result ingredients and
keys, and `request()` emits precisely its
`StagedInput` names/paths/identities. Source/code data files stage read-only with canonical mode 0444;
item members preserve their semantic executable distinction (read-only 0444/0555 while staged).

C1 must implement this boundary: it may not inject original source locators, selector text or producer
history through Run fields, parameters, logical input objects, environment or helper APIs. Parameters
are the declared semantic parameters, not an implicit metadata channel. The op sees only the hashed
staged view. Job ID, job directory and unit scheduling label remain controller/logging metadata and
must not influence semantic output. The pending `c1.staged-view-semantic-independence` scenario requires
actual worker output equality under different control metadata and source locators; logs may differ.
A3 tests establish encoding and Run mapping only, not that future workers already enforce isolation.

**Result schema 3:** `IdentityIngredients.script` identifies the selected entrypoint even when the code
closure is unchanged; `staged_inputs` records the visible slot map and `input_kinds` binds each slot
as a file or item directory, even if content digests coincide. `StoredFile.mode` is 0644 or 0755.
B1 blob hashes remain byte-only and stored blobs immutable. B2 must normalize captured source mode
(any execute bit becomes 0755, otherwise 0644), retain it in result records and compare it for conflicts;
B3 must restore semantic modes before publishing checkout installs. C1/B2/B3 and package tests must
prove those mode rules. General ACL/xattr handling is outside this format. Old result records lack
these required fields; B2 must reject unsupported result versions rather than infer missing metadata.
Declaration schema 2 adds fixed output groups and selected member references; fixed schema1
declarations remain readable. Result3 adds required group contracts/runtime membership; key encoding2
binds fixed group contracts. Worker framing protocol remains version1.

`SourceHashCache` hashes each frozen whole-file or selected-view version once. Its advisory version
hint includes device, inode, size, nanosecond mtime and ctime; selector hints also identify the selected
view and its explicit encoding version. A changed view codec must bump that version before reusing hints.
Hint metadata never affects the semantic hash. A changed ctime defeats an unchanged-size/mtime
hint. Missing hints hash bytes; missing/corrupt checksummed hint records become empty caches. The
snapshot provider must bind stat tokens to those same frozen bytes. The checksum detects damaged
hint records; it is not a hostile-input trust boundary. Live source snapshotting, input rechecks,
mid-build rekeying, actual scheduling cutoff and clean-build oracle integration remain later work.

`tests/keys.rs` covers the identity boundaries, selected-data cutoff, reference independence, semantic
modes, staged paths, dispatch metadata, manual invalidation, source-version reuse and damaged hints.
The broad engine scenarios in the registry remain pending until the engine/reference model exists;
these pure tests do not claim A4/A6/A9 end-to-end execution behavior.

## Failure policy (C5a)

`failure_policy::JobPolicy` makes pure per-job decisions from caller-supplied monotonic times and
controller-side `Event`s; it reads no clock, never sleeps and launches or signals nothing. Only a
controller-observed unexpected exit on the first attempt is retry-eligible; the retry waits for
confirmed cleanup and then asks for a fresh admission (`RequestAdmission`), launching only after
`Admitted`. A worker's own `failed` claim, including `crash`, is never crash evidence. Job, dependency
and protocol errors, cancellation, job-limit and overall-deadline timeouts, guard stops and cleanup
timeouts do not retry; such a fact or a cancellation during crash cleanup withdraws the pending
retry. The job limit starts at each admission; the optional overall deadline runs from
submission over queue, execution, cleanup and retries. `BeginCleanup` is a request limited to the
owned process and unpublished scratch, and an `Unconfirmed` cleanup outcome means the process may
still be alive. Real owned-process cleanup (C5b) and capacity/guard integration (C7) remain pending.
The decision matrix is in `tests/failure_policy.rs`.

## Selected static graph (A4a)

`graph::BuildGraph::validate` owns a declaration after global A2 structural checks: supported op
slots, parameters, paths, unique owners, complete references and an acyclic graph. It does not
require every declared source to be available. `select(targets, snapshot)` chooses explicit unit IDs,
dot-delimited namespaces or all units, then observes sources and selectors only within that target
closure. A missing source for an unrelated unit does not block a focused build; selecting that unit
refuses before any dispatch. The existing public A2 `validate` still validates all sources.

Both content and declared reference producers precede consumers. An external reference with no
producer adds no invented edge. Selection exposes read-only roots, deterministic dependency-first
order, role/item-tagged edges and the matching A2 source observations for later A3 preparation.
Repeated or overlapping targets are a set union; an unknown or empty target selection refuses.
No source file is opened by this API: the caller supplies the immutable snapshot.

This is **A4a only**. Dynamic `plan.json` validation, stable generated children and removed-owner
intents remain A4b, coordinated with the D2/Editor Cost plan interface. No worker dispatch, store
lookup, materialisation, install/removal or scheduler/output-cutoff proof is implemented here.

## Worker session and Python framing (C1a)

`worker_session::Session` is the controller-side order of one worker conversation: `hello` with the
expected worker version, then one job at a time (`run`, `started`, exactly one `completed`/`failed`
with the same job ID), and `shutdown` only while idle, answered by `stopped` and a clean end of stream.
Job IDs are unique per session. A malformed frame, wrong version or job ID, out-of-order or duplicate
response breaks the session (`Protocol`); an end of stream or failed write outside a clean close is
`Disconnected`; a refused controller call (`Misuse`) leaves the state unchanged. `cancel` records a
request; only `failed` of kind `cancelled` confirms it, and a job that finished first still reports
`completed`. `Channel` drives a session over any framed reader/writer pair. It builds each frame
before writing, so any later write or flush error breaks the session. `protocol::read_frame` refuses
duplicate keys and positional (array) envelopes, messages and records, so such a response breaks the
session as a malformed frame.

Worker rule: a worker MUST send `started` for every `run` before its single terminal response,
including a job it rejects at once and a `cancel` that arrives before it started. A `cancel` that
arrives after the job's terminal response gets no reply.

The session passes job requests through unchanged and only refuses empty IDs or worker-facing names
that are absolute, contain `.`/`..`/empty components, backslashes or NUL. Staging and the full path
policy (C1b, A3), execution (C2), deadlines, retries and crash classification (C5) and admission (C7)
are not here; nor is validation of returned output paths.

`platform/studio/atelier/build_v2/protocol.py` is the standard-library Python framing: the same frames,
size limit and strict shapes, as plain dicts, encoded with stdlib `json`. Interoperability means equal
decoded values, not identical text: no key, digest or comparison consumes wire bytes (keys are computed
in Rust from typed values, and responses carry no numbers). [tests/vectors/protocol_v1.json](tests/vectors/protocol_v1.json)
holds byte vectors that both `tests/worker_session.rs` and `platform/studio/tests/test_build_v2_protocol.py`
decode to the same values; canonical vectors also pin Rust's own text. The pipe tests start
[tests/fixtures/fake_worker.py](tests/fixtures/fake_worker.py) with its protocol on two inherited pipe
descriptors and logs on stdout/stderr, under a five-second watchdog; the Rust T0 job needs `python3`.

## Staging and the Python job loop (C1b, C2a)

`staging::stage(&PreparedUnit, frozen_code, objects, job_dir, job_id)` creates a fresh job folder (it
must not exist) holding exactly the unit's declared code and inputs at their declared job-relative
paths, plus an empty writable `output/`. Code bytes come from the frozen snapshot A3 keyed, checked
against the keyed digests; live sources are never reread. `Bytes` inputs (raw, selected or reference
descriptors) are files; `Item` inputs are directories of exactly their recorded members, cloned through
an `ObjectSource` with their recorded size; optional absence creates nothing. Files stage 0444 (item
executables 0555) and every directory except `output/` is made 0555. `PinnedObjects` clones B1 objects
while a live B2 `WriteTransaction` (which claims the upstream result keys) is borrowed; restores clone
and hash nothing. Staging failure removes only its own fresh folder. The request it returns names the
staged paths and drops output `install_path`s; locators, selectors and logical paths never appear.

`staging::collect_outputs` walks `output/` without following links and requires the worker's reported
files to equal the regular files found. It returns every actual file as `results::ActualOutput` (path and
source), declared or not, which is exactly what `WriteTransaction::stage_groups` consumes: fixed outputs
and group members alike reach the result store, which holds the exact contracts and decides
membership; nothing hashes here. `fixed_sources` maps a fixed-only unit's
files to their items for B2's `WriteTransaction::stage` and refuses any other file.
`remove_job` deletes a job folder after B2 has staged or refused its outputs.

`launch::StartWorker` is the launcher seam: start a `WorkerCommand` (program, args, complete
environment, working folder) with a dedicated pipe, appending `--request-fd N --response-fd M`, and
later `stop` or `wait` it. C7's supervised launcher implements it with admission, guards and deadlines;
`DirectChild` starts an owned child for tests and local tools only. `launch::run_staged` runs one
staged job: handshake, the staged request, then `collect_outputs` on `completed`; failures, protocol
breaks and reported/actual mismatches give no outputs, and a broken worker is stopped. Nothing is published
or deleted there.

`platform/studio/atelier/build_v2/python_worker.py` is the Python job loop. It makes both protocol
descriptors non-inheritable at startup, sends `hello` (`atelier-python-job-1`), and for each `run`
sends `started`, runs the job in its own child process and sends one terminal response; `cancel` kills
that child and answers `cancelled`. The child runs `python -P -s -S -B` with the bootstrap
`python_job.py` passed as source text, in the job folder, with only `LC_ALL=C`, `TZ=UTC`,
`PYTHONHASHSEED=0` and two Python I/O settings. The entry script defines `run(context)`; the
`JobContext` (documented in `python_job.py`) exposes slot paths (`None` when absent), read-only params,
declared outputs and the seed, never the job ID, folder or any locator. Only platform modules and the
unit's declared code load, and the checkout is never on `sys.path`. Under `-S` the child cannot find
the loop's virtual environment itself, so the loop passes its own purelib and platlib folders in the
child's configuration; the child appends exactly those, after the standard library, and refuses the
job when one is missing or resolves outside the platform roots. No `.pth` file runs. Wall-clock reads (including
`clock_gettime` of realtime clocks) return a fixed instant, `random` is seeded with the declared
`seed` (default 0) even when reseeded without an argument, and OS entropy, `uuid1/4` and `secrets`
raise; this makes ordinary scripts reproducible, not the OS deterministic. Elapsed-time clocks, file
timestamps and native-library random generators are not fixed: outputs must not depend on them.
The job configuration travels on the child's stdin, so no valid request can exceed argument limits,
and a failure to start the child still gives the job its one terminal `failed` response.

On macOS each child runs under a deny-default `sandbox-exec` profile: it may read the installed
interpreter and its libraries, a few platform files (locale, time zone, user database) and its job
folder, and write only `output/`. Any other existing path read, stat or listing, and any network use,
kills the child, which the loop reports as `failed{dependency}` (the loop itself is never killed, so
C7 sees no crash). The kernel reports a missing path as ENOENT without a sandbox decision, so a Python
path guard (an audit hook plus checked `os.stat`/`lstat`/`access`) also ends the job, uncatchably, on
any undeclared read, existence check, listing or write, present or missing (descriptor-relative
`dir_fd` access is resolved against the descriptor's real directory, and directory changes are
refused), and on process starts,
links and sockets. Elsewhere jobs fail with `dependency`: the production entry has no unsandboxed mode at all. The
profile lets the child execute only the interpreter binary (and a framework build's re-executed
`Python.app`). Portable tests reach an unsandboxed loop only through the test-only entry
[tests/fixtures/unsandboxed_job_loop.py](tests/fixtures/unsandboxed_job_loop.py), which announces
`atelier-python-job-1+unsandboxed-test`; a session keyed to the production worker version refuses it,
so its results can never pass for production ones.
The loop reports every regular file under `output/` (any group folder there is writable too) and fails
on links or special files; membership is the controller's.

**Scope.** Job code is trusted project code. The macOS kernel filesystem and network sandbox is the
enforcement. The Python guard is extra detection of *accidental* undeclared dependencies, not an
adversarial Python jail. A real bug in a supported check is still a bug to fix; this scope is not a
blanket exception.

Supported Python-level checks:
- reads, existence checks and listings, by path or by descriptor (`dir_fd`, or a descriptor in place
  of a path), resolved against the job folder or the descriptor's real directory;
- writes outside `output/`;
- refused directory changes, links, process starts, sockets and named `ctypes` libraries;
- imports limited to installed platform modules and the declared code, and new import path entries
  (`sys.path` or package paths) that are undeclared fail when probed, present or missing;
- fixed wall clocks (`time.time`/`time_ns`, default `localtime`/`gmtime`/`ctime`/`strftime`,
  `datetime` now/today, `clock_gettime` of realtime clocks);
- `random` on the declared seed, including `random.seed()` and `Random()`;
- refused Python entropy APIs (`os.urandom`, `getrandom`, `uuid1/4`, `SystemRandom`, `secrets`).

Known gaps, which these checks do not intercept:
- native extension code that probes a *missing* undeclared path through the C library (an existing
  one is still killed by the kernel), so nothing here proves undeclared absence probes cannot happen;
- monotonic, performance-counter and CPU-time clocks, and file timestamps, which stay real;
- random generators in native libraries that read OS entropy themselves;
- deliberate tampering with the guard itself: removing the import path hook or the declared-code
  finder is detected when the op returns, but code that removes and restores them, or restores the
  original `os` functions, is outside this trusted-code scope.

Unit code MUST NOT derive outputs from real clocks, timestamps or native entropy. Clean-room and
determinism fixtures remain required.

Other open work: Linux has no sandbox yet. The worker implementation digest, B3 installs, A6 live-edit
revalidation and C3/C7 supervision are not here.

## C2b Blender job loop

`platform/studio/atelier/build_v2/blender_worker.py` is the Blender job loop. `launch::WorkerCommand::blender_job_loop`
starts it inside the installed background Blender as
`Blender --factory-startup -b --threads 3 --python-exit-code 1 --disable-autoexec -P blender_worker.py --`; the
launcher appends the protocol descriptors after `--`. The thread count precedes `-P`, so capacity admission
reads three threads rather than the full pool. The loop is the Python job loop with another platform and
child command: the same protocol, cancel and output reporting, and its own `hello` version
(`atelier-blender-job-1`, `launch::BLENDER_JOB_LOOP_VERSION`). One loop serves any number of jobs; it holds no
Blender state itself.

Each job runs in a fresh Blender from the same binary (`bpy.app.binary_path`), in the staged job folder:
the loop's flags plus `--python-use-system-env`, then `--python-expr` with the bootstrap `blender_job.py`
and the Python job bootstrap `python_job.py` as source text. The configuration arrives on stdin. The
bootstrap resets the scene to an empty factory file (`read_factory_settings(use_empty=True)`) and runs
the Python job bootstrap, so a Blender op is `def run(context)` with `bpy` importable and the whole
Python job isolation above applies. The environment is the Python job's (`LC_ALL=C`, `TZ=UTC`,
`PYTHONHASHSEED=0`, two Python I/O settings), with `--python-use-system-env` so the embedded Python
honours it, plus `HOME` and every `BLENDER_USER_*` folder (resources, config, scripts, datafiles,
extensions) pointed at a missing path inside the job folder. With `--factory-startup` no user
preferences, startup file, add-ons, extensions or scripts load; only Blender's bundled add-ons are
available. A new process per job means no scene, module or interpreter state reaches the next job.
Two Blender-only adjustments to the Python job bootstrap, both in `blender_job.py`: `uuid.uuid4()`
returns UUIDs drawn from the declared seed through its own generator, because the bundled glTF
exporter keys its node tree with them (`uuid1`, `os.urandom`, `secrets` and `SystemRandom` still
raise); and the undeclared-module check skips the module objects Blender's own startup loaded before
the bootstrap (`__main__`, add-on and extension namespace packages, some named after the missing user
folders), which are platform. Blender's bundled Python has no `time.clock_gettime`, so there is no
realtime clock of that kind to fix. With `--python-use-system-env` the declared `PYTHONHASHSEED=0`
applies: string hashes are the same in every job and process.

On macOS the child runs under the Python job profile with the Blender application bundle as the
platform: it may execute only the Blender binary (its path, links and target), read the bundle, the
platform files of the Python profile and its job folder, and write only `output/`. Added allowances,
each needed by Blender itself:
- the application bundle (`Blender.app`), as a read subpath: Blender's binary, bundled Python, `bpy`
  modules, bundled add-ons and data files;
- `/usr/share/icu`, as a read subpath: the system ICU data Blender loads at startup;
- `/Library/Preferences/.GlobalPreferences.plist`, as a read literal: the system-wide (not per-user)
  CoreFoundation preferences read at startup;
- opening the GPU's IOKit user clients (`AGXDeviceUserClient`, `IOSurfaceRootUserClient`), no file
  access: Blender probes the Metal device during startup even in background mode and crashes
  (SIGSEGV in its GPU backend detection) without one;
- metadata only (no listing) of `/tmp` (`/private/tmp`) and `/Applications/Xcode.app`: Blender's
  temp-folder probe and a system framework's developer-folder probe at startup; writes to `/tmp` stay
  denied, so Blender runs without a temp folder;
- reading `/dev/urandom` in the kernel profile only: the bundled Python's `os.urandom` reads it and the
  bundled extensions add-on calls it at startup. Job code still cannot: the guard refuses
  `os.urandom` and opening `/dev/urandom`;
- binding a socket is refused without ending the job (a later `(deny network-bind)` replaces the
  kill for binds only): the bundled HTTP library, imported by the extensions add-on at startup,
  probes IPv6 support by binding a local socket. Connections and all other network use still end the
  job, and job code cannot create sockets at all.

Nothing in the home folder is readable: user preferences, `~/Library` and caches stay denied, and
user-database, temp-folder and window-server service lookups stay denied without ending the job.

The Python guard does not see Blender's native (C) file access: an existing undeclared path read
natively (for example `bpy.data.images.load`) is stopped by the kernel sandbox and fails the job as
`dependency`; a native probe of a *missing* undeclared path is the same documented gap as for Python
native extensions (in the T1b session the probe used, `bpy.data.images.load` of a missing file in an
existing undeclared folder, was still stopped by the kernel, but that is not a guarantee). Installed Blender and its bundled add-ons are platform, not key ingredients; a
change of Blender is an explicit cache or op version change.

## B2 fixed-result publication and leases

`ResultStore::begin(&PreparedUnit, provenance, owner, workers, upstream_keys)` persists a unique
staging-scope lease before creating that scope. Process identities bind PID, boot and start identity;
the lifecycle adapter must probe that same identity. Unknown liveness is conservative. No clock-only
expiry or process signaling is provided here.
Warm workers may be listed at begin; `add_worker(identity)` durably registers a newly launched worker
before the lifecycle adapter allows it to write. The startup barrier and OS probes remain C5b/C7 work.
The initial lease claims both the consumer key and supplied upstream result keys, so producer records
remain protected before a complete consumer record exists for retention traversal.

`WriteTransaction::stage(OutputSources, validator)` consumes the complete authoritative worker output
manifest keyed by `(item_id, output_relative_path)`. Unknown paths and missing required members refuse;
optional sidecars may be absent. C1 must supply the whole actual manifest, including any unexpected
members, rather than filter it first. B2 does not rediscover that manifest by scanning a live directory.
Each source is independently cloned, frozen, hashed once and given to the format validator through
`FrozenOutput.object.reader()`. The opaque reader exposes those exact frozen bytes, never a second live
source read or a writable handle. Only successful validation yields a private `StagedResult` token.

`StagedResult::publish(required_durable_root_callback)` durably adds all known object claims under
`LeaseStore::lock()`, publishes immutable blobs, publishes a no-replace read-only result record, invokes
the required root callback, then releases the per-unit object/result claims. Immutable JSON metadata
uses an exclusive hard link from private staging; it never hard-links payloads or mutable output trees.
The callback must durably retain the winning result before returning success; B4 chooses root policy.
It runs outside the metadata mutex so it can acquire that same mutex for its own metadata update.
Callback failure or an interrupted step preserves claims. The observer API provides fault injection
after each durable publication boundary; it does not bypass ordering.

`lookup()` on a live transaction reads only the named result and named object metadata, pins the
recorded objects under the shared mutex, and performs no byte hash or output-tree walk. Keep this
transaction alive while consuming/cloning the hit, then call `retain_hit(required_root_callback)`.
Missing or malformed entries return absence/error; B7 defines higher-level miss/current-but-not-cached
handling. Whole-store corruption auditing remains separate.

Envelope version 1 wraps result schema 3 and `upstream_result_keys` for future retention traversal.
Those links, provenance and unit labels never participate in semantic winner equality. The first
winner retains its own immutable lineage/evidence even when an equivalent unit has another graph ID.
Different complete output manifests, including file modes, report non-determinism without replacing
the winner. External/Zen adapters remain unsupported; groups use the separately validated complete-manifest entrypoint.

Per-unit claim release marks the lease rooted but retains its process/staging header. Dropping a
transaction also preserves durable claims. A later lifecycle/GC adapter may reclaim a scope only when
the owner and every worker are positively dead; `may_reclaim()` refuses alive/unknown identities.
All such decisions and deletions must hold the same persistent `metadata.lock` inode through the
public `LeaseStore::lock()` guard; never remove that mutex file. `MetadataGuard::leases()` fails closed
on malformed/unsupported records. B2 does not implement root selection, scope deletion, checkout
installs, OS process probing, age-based retention or GC. Production v1 remains unchanged.

## Roots, provenance and build sessions (B4)

`roots::RootStore::open(store_root, project)` names one explicit project inside an existing
trusted canonical store (a missing store root is refused) and takes the store's `metadata.lock`
inode through its own `LeaseStore` handle. Roots live under `roots/<project>/`:
`main.json`, `worktree/<id>.json`, `release/<sequence>.json`,
`pin/<id>.json`, in-flight `session/<id>.jsonl` and a private `tmp/` for atomic
writes. A root is a map from the unit's scheduling label to that unit's last result key, and each
entry keeps the provenance of the session that wrote it; `RootRecord::provenance` describes
only the most recent merge. Roots and provenance never enter cache identity.

Beside `roots/`, the store keeps `meta/projects.json`: every initialized project with a
creation time and a digest bound to its exact name. The first time a project is initialized,
`open` writes that record under the metadata guard with a temporary file, fsync, rename and a
parent-directory fsync. A registered project is never recreated: a fresh `open` after
`roots/<project>`, all of `roots/` or the registry itself is lost is damage, so retention can
never report a silently empty project. No production v2 store exists yet, so a store built before
this record (with `roots/` but no registry) also reads as damage: there is no silent migration.

`RootStore::begin_session(target, provenance, owner)` creates a build session whose header
records the owner identity. `BuildSession::use_result` appends `(unit, key)` to an
append-only journal and fsyncs it; `root_callback(unit)` is the exact
`FnOnce(&ResultEnvelope) -> Result<(), String>` that `StagedResult::publish` and
`WriteTransaction::retain_hit` accept, so a result is retained before B2 clears its claims.
The caller names the unit: the winning envelope's `unit` may belong to an earlier equivalent
producer. A session keeps every key it used, including retries and re-keys, and the commit keeps the
last key per unit. Each call takes the store flock and fsyncs one small append; nothing rewrites the
whole root per unit.

`commit(declared)` merges a main or worktree root with the current one inside a single
metadata-lock hold. Without a `DeclaredRoster` nothing is pruned; a roster can only be built
from a full `validate()` result whose dependency order covers exactly the declaration's
units, and entries outside it are dropped. A release or pin is a frozen snapshot written whole and
never merged. Releases are identified by an explicit sequence; an existing sequence with different
entries is a conflict, an identical retry keeps the first record, a sequence below the retained
window is refused before anything is written, and only the three greatest sequences survive. Pins
are never trimmed. `snapshot` freezes an existing root into a release or pin.

A torn, unterminated or otherwise invalid journal record makes `commit` fail and leaves both
the previous root and the journal untouched. A failed append truncates back to its previous length,
so it cannot leave a torn tail. `commit_observed` exposes the same boundaries as B2's
publication steps for fault tests, after the lock. Temporary files live in `tmp/` and are
swept by the next lock holder, so a crash between write and rename never damages the listing.

`retention()` counts every key named by any readable root or session and reports unreadable
records instead of guessing: B5 must retain when that list is not empty.
`retention_locked(guard)` and `roots_locked(guard)` read under a caller-held guard, so
GC reads retention, leases and decides deletions under one lock hold; a missing metadata directory is
damage, not an empty view. `sessions()` lists session headers and
`release_dead_session(id, probe, custodians, cleanup)` removes a journal only when its owner is
positively dead and, if the owner is a registered custodian, C5c's cleanup is confirmed.

`may_reclaim(lease, probe, custodians, cleanup)` is the only public reclaim decision. Every
owner and worker identity must be positively dead, and a dead registered session custodian keeps the
lease retained as unknown liveness until C5c's cleanup record is durably confirmed. An unreadable
correlation or cleanup record also retains, and a dead monitor process alone never proves cleanup.
The custodian registry and confirmation are traits (`SessionCustodians`,
`CustodianCleanup`) until C5c lands its durable store. B4 deletes root records and its own
journals only; result records, objects and leases are untouched, and no root is removed because a
checkout directory disappeared.

## Bounded groups and typed child expansion (A4b)

`groups` reads the existing D2 schema1 plan envelope and checks complete flat membership, authored
names, encoding, budgets, payload digests and whole-collision ownership. Payload geometry stays
opaque; a source-specific validator must inspect the same B1 frozen objects before a private
`ValidatedGroup` can exist. `PlanRoster` alone is discovery metadata, never a format certificate.
The retained Village_Edges plan fixture is source-format evidence, not native acceptance.

A fixed `OutputGroupContract` owns an exclusive job-output-relative root, including its manifest.
A manifest or payload cannot also be a fixed output; auxiliary query/runtime outputs remain
explicitly outside that group or in separately declared groups. The worker output-root parameter
is declared and keyed and must equal `output/<group.root>`. Run/protocol v1 stays unchanged: the
controller obtains group contracts from exact prepared ingredients; Run.outputs remains its fixed
file portion. Future C1b must report all fixed plus group output membership and reject unknown,
aliasing or over-budget members. C1a framing alone proves none of that group behavior.

Selected projections reuse one-member Item staging and bind that member's logical identity,
path, byte digest, size, mode and certified encoding/role. A complete saved manifest can restore a token through B2's
trusted reader with named object checks, without scanning mutable output folders. Group/roster
changes remain separate from a selected member's content view.

This slice remains unused by production callers. Declaration2/result3/key2 bind fixed groups and
selected member identities. `stage_groups` partitions one complete actual fixed+group list, freezes
under the existing lease and invokes source validators on those snapshots; every group object,
including the plan, is claimed before publication. Full groups/projections participate in winner
equality. The old `stage` API refuses group units. `lookup_groups` restores private tokens only after
trusted record checks, named CAS metadata checks and durable pins under the same GC mutex; it reads
no plan bytes and scans no output folders. C1b must supply the complete actual manifest and preserve
physical sandbox boundaries; these APIs do not implement a worker or a filesystem sandbox.

`plans::RegisteredTemplate` binds a programmatic `ChildTemplate` to a fixed planner/group contract.
The template supplies the exporter op, script, explicit code closure, parameters, staged payload slot
and fixed store-only output files. Plan rows supply only validated member metadata. A child uses a narrow
`GroupMember` dependency and stable `<unit_prefix>.<piece>` ID; its logical output ends in the same
piece name. Export parameters name that selected member, encoding and certified role. No planner code closure,
whole roster or producer input key enters the child contract. Key tests prove the pure identity
boundary; actual skipped worker launches remain D2/A9 acceptance.

Cold child selection reports `NeedsPlanner` until validated membership exists, then `Ready` or
`UnknownChild`; it never exports a provisional unit or fictional hit. `expand` checks all generated
children with the same global structural validator before returning a graph. It does not require
unselected source observations. Its private in-process `ExpansionReceipt` records exact generated
units. Re-expansion checks the stable producer/group/unit-prefix/logical-namespace ownership scope
and unchanged prior units; exporter code/op versions and planner versions/budgets may evolve. Removed children yield exact prior export-Item `RemovalIntent`s, without deleting files or
inferring ownership from a prefix. A persisted previous group may be re-expanded to reconstruct its
receipt; raw deserialization cannot mint one. Current D2 schema1 validation refuses zero-piece plans;
retiring an entire empty family needs an explicit reviewed empty-plan contract.

C1b still owns complete physical output reporting/sandboxing; D2 binds real recipe templates and A9
schedules planners/children. D4/A5 must supply downstream installed ownership/reference views before
B3 can preflight and apply native-package removals; prior export Items alone do not certify those deletions. No worker execution,
install/removal, production activation or native equivalence is claimed.

B3 introduces an unused checkout-install boundary in `install` and `checkout_locks`.
A restore plan pins a validated cached result, checks the complete current ownership view,
and installs only explicit Checkout mappings under build and exclusive content custody.
Its journal precedes staged clones and records exact prior/new names; immutable item receipts
are indexed by explicit project namespace plus logical item path. Recovery rolls back before
the receipt-index commit and finishes owned cleanup afterward. Unknown leaves preserve the
journal and block readers. Modes are replayed from result metadata; cache hits do not hash
payloads, copy bytes, or scan output folders. Root failure after commit preserves installed
receipts and conservative cache claims. B4/B5 root/GC policy, B7 fallback, and real C7 monitor
custody/caller integration remain separate; the custody accessor alone is not lifecycle proof.
The macOS APFS tests cover transaction rollback and resumable pre-install abort. Before
the Ready marker, a crash (including clone return before inode observation) can abort only
after verifying the unchanged old index and exact old file
observations, absent trash, and the pre-owned scope directory identity. Recovery journals an
abort intent, durably archives the SHA-bound journal, and atomically quarantines the entire
private scope without adopting/deleting unknown leaves. It rechecks the old checkout and
preserved evidence before clearing the reader barrier. Every abort transition is resumable;
invalid identities, changed old files and post-mutation uncertainty remain blocked.

Quarantine retains independent clones, exact journal evidence and explicit process/result/object
claim metadata. The failed B2 lease is unchanged; quarantine is not an immortal CAS pin or
successful result. Future B5 dead-producer CAS policy and explicit quarantine artifact cleanup
are separate. No automatic quarantine cleanup, payload rehash, tree discovery or new CLI exists.
A dirty original inode remains managed and its current bytes are preserved for rollback;
a replacement inode at an old receipt-owned name refuses both restore and retirement.

`ReceiptReader::open(checkout, policy)` checks Current/Dirty/NotMaterialized through the same
receipt/index/stat validator without opening or creating a cache. `CheckoutInstaller` composes
that reader with cache capabilities. A fresh receipt reader therefore preserves a valid Current
result even when a cold-start cache open would fail. B4/B5/B7 and actual C7 caller integration
remain separate; this unused library is not production-cutover acceptance.

For demand materialization, `lookup_restore` returns `RestoreLookup::Miss(WriteTransaction)`
or `Hit(RestorePlan)`, preserving the original miss lease for dispatch. A pinned hit can be
rooted via `retain_cached` without installing checkout files. The older `prepare_restore`
wrapper conservatively drops a miss; new scheduling callers use the explicit enum. Stored-only
planner token lookup remains B2 `lookup_groups`; no parallel graph/controller lives here.
Current checks and install preflight share the complete owner-to-index membership validator;
an extra indexed path cannot certify Current. Postcommit cleanup is resumable after each owned
leaf/directory removal, including an already-removed scope parent. New scope allocation reserves
both transaction and quarantine namespaces, including dangling entries, across PID reuse.
Unknown private cleanup leaves keep the active journal and reader barrier; populated checkout
output parents are preserved without requiring them to be empty.

## Offline verification and integrity classification (B7a)

`verify::Verifier` provides opt-in, read-only verification of stored result records, output manifests
and payload objects (`VerificationMode::Full` or `VerificationMode::Sampled`). Normal lookup
(`results::WriteTransaction::lookup`) and restoration (`store::ObjectStore::clone_to`) check
metadata/size and clone without rehashing payload bytes; `Verifier` streams and SHA-256 hashes the
actual stored object bytes from disk, bypassing stat/version hash hints, and reports `Verified`,
`Missing`, `MissingObjects`, `Corrupt`, `Malformed`, `IncompleteManifest`,
`Unsupported`, `External` and `Unverified` separately. Sample-skipped items, non-empty
`output_groups` records or contracts (`UnsupportedReason::OutputGroupsUnsupported`), and external
Zen references never report `Verified`.

While inspecting records and objects, `Verifier` pins the target result keys and discovered manifest
object digests through `leases::LeaseStore::begin` and `MetadataGuard::save` under the shared
metadata mutex. Because `LeaseStore::begin` reserves a matching empty `staging/<id>` directory
as part of the lease invariant, the verifier creates that empty directory when acquiring the lease, never
writes inside `staging/`, `objects/` or `results/`, and releases its claims and removes
the empty `staging/<id>` directory via a `Drop` guard on every exit path (normal return, error
or panic). If a process is killed abruptly before `Drop`, only a normal owner-identified lease
remains, which `LeaseRecord::may_reclaim` reclaims once the owner is dead.

`integrity` exports pure, narrow decision types (`LookupDecision`, `RestoreDecision`,
`CompletionDecision`, `NonHitReason`, `StoreFailureKind`, `UnitFailureReason`) for
later B7/A5/A9 integration. Store, lease, clone or root failures after local output validation preserve
valid work as `CompletedNotCached`, whereas invalid producer outputs, validator rejections and
same-key nondeterminism fail the unit.

## B7 local completion and availability capabilities

`WriteTransaction::lookup_recorded` returns sealed `RecordedIdentities`: exact prepared key,
ingredients and complete fixed/group metadata, under the existing result-key lease and GC mutex.
It never probes payload objects. Its selected group projections preserve encoding/role metadata;
they cannot become available `ValidatedGroup` tokens. `lookup_groups` retains its existing complete
object checks and pins. A valid recorded identity can therefore resolve a consumer key before an
unneeded missing producer blob forces work. Normal producer-under-consumer retention prevents the
common eviction case; missing/corrupt entries still return typed absence/failure. An adapter that
cannot validate identity without missing payload bytes must refuse rather than invent authority.

`ReceiptReader::pin_current_sources` reuses the cache-free complete receipt/stat validator, holds
shared read custody and pins no-follow regular file descriptors. `objects_for` binds the consumer's
exact item content/modes before its `ObjectSource` provider can clone. The provider uses APFS fd
clones and pre/post observations, with typed `Unavailable`, `Changed`, `CloneUnsupported` or `Io`
errors; it never copies, hashes, reopens source paths or chmods. C1b applies keyed read-only modes.
Drop custody immediately after `stage`: job clones are independent, so worker execution does not
block checkout installs. A5's public Current receipt vectors are diagnostic, not this capability.
Checkout receipts cannot certify missing store-only outputs or group manifests. No automatic partial
backfill is provided; complete result publication requires all fixed/group/auxiliary snapshots.

`ReceiptReader::begin_completion` creates an existing-format local owner/worker lease under reserved
install metadata before job/snapshot writes. Its job directory is suitable for C1b staging; register
new workers before allowing writes. `CompletionWork::freeze` takes the complete authoritative actual
output list and shares B2's fixed/group validation core. Validators read the same private snapshots
that B1 hashes once. A read-only complete envelope plus named snapshot locations is durably recorded.
`FrozenCompletion::publish_with` consumes the original A5/A9 miss write transaction, held through
staging/run, and adopts independent verified clones without rehashing. The `publish(store, root)`
convenience creates a late transaction only when none existed because the cache was unavailable. Local evidence survives every attempt; semantic conflicts latch a hard refusal.

`ReceiptReader::prepare_local` accepts only that sealed completion, never opens CAS and uses the same
RestorePlan journals, ownership checks, modes, atomic receipt/index publication and recovery as cached
restoration. Same-key prior receipts are checked for nondeterminism before preparation and again
under commit custody. A successful local commit returns `InstalledLocally`, separately reporting
local retention failure, and does not call the cached-result root callback. Its exact receipt/index
is the durable checkout authority; it is Current without asserting cache availability. Local artifacts
and owner evidence remain retained, including after quarantine recovery. They are not immortal shared
CAS pins and introduce no cleanup CLI/service. Production scheduling and the guard/cleanup liveness
adapter remain separately reviewed integrations.

## Unit demand (A5)

The unused `demand` module separates checkout satisfaction from stored availability.
`checkout` first uses B3's cache-independent receipt reader. A current target returns
without invoking the lazy cache opener or rewriting output, receipt or index files.
Explicit retirement intents still require preflight even when surviving outputs are
current. Dirty/absent targets use one B3 `lookup_restore`; misses retain that original
write transaction, and hits return the existing install plan. Lock, recovery and
ownership refusals remain hard errors rather than a reason to bypass install custody.
Retirement authority is checked by B3's cache-free preflight before the lazy opener;
constructor and B2 errors carry an explicit cache-origin wrapper. An invalid receipt
ID, stale authority or malformed checkout metadata cannot become a cache miss merely
because its low-level error uses a store digest type.

`stored` uses B2's checked, durably pinned `lookup_groups`, exposing recorded content and
private group tokens through a `StoredHit`. It never installs checkout files. Rooting
delegates to B2; failed root callbacks retain claims. Missing/damaged/unavailable stores
use B7a typed non-hit classifiers without offline verification, byte-copy fallback or
payload rehashing. A miss without a transaction does not authorize unleased writes.

The caller supplies an already prepared exact key and a matching checkout/project cache
opener. These functions do not select, key, traverse, dispatch or stage ancestors: a
satisfied final demand returns immediately. Tests use an A4-selected two-unit reference
closure and a real cached final result with no intermediate result to prove this API
does not materialize prerequisites. This does not prove cold key resolution, dynamic
planner scheduling, worker staging or A9's end-to-end dispatch/output cutoff; those
integration obligations remain separate. The complete ownership view and exact
retirement authority still come from B3/D4 callers, never path-prefix inference.

`FrozenCompletion::available_groups` restores available local group tokens only after checking every
named member against its fully validated private frozen snapshots, including normalized modes.
`objects_for` binds complete selected consumer item views and returns borrowed `FrozenObjects` for
clone-only C1b staging. These are local byte capabilities, not CAS hits; missing/corrupt named local
snapshots refuse rather than becoming available from recorded metadata alone. The producer can stay
completed while a downstream miss uses preserved store-only/group bytes without rerunning it.

`ReceiptReader::current_identities` issues a sealed metadata observation using the shared Current
validator under temporary read custody. It retains no guard or FD, so identity-only hits cannot block
later installs. Stage-time CurrentSources reacquires and revalidates exact selected content/modes.
FrozenObjects selection checks only selected bytes from sealed recorded views: loss of an unrelated
sibling refuses a full available group token but does not prevent staging a surviving selected member.

## Static scheduling core (A9a)

The unused `scheduler` module binds one A4 selected graph and immutable snapshot,
resolves exact A3 keys from producer output identities, and looks up all ready units
before submitting a compatible miss batch. After each batch it refreshes the frontier,
retaining original undispatched miss tickets. Completions publish independently;
failures block dependents while preserving unrelated publications. Missing terminal
outcomes stop further dispatch because cleanup is unresolved. Cancellation requires
explicit terminal settlement for every submitted handle.

Three purposes remain separate. Explicit final demands are sets of Stored and/or
Checkout, while internal prerequisites have no final demand. Recorded identity and
short-lived Current observations can resolve consumer keys without stored availability.
Recorded cannot satisfy a final demand; Current cannot certify Stored. Identity-only
Current observations must release their short checkout read custody before lookup
returns. No public receipt vector constructs byte availability.

Only an actual consumer miss calls `prepare_inputs`, immediately before dispatch.
The backend acquires and revalidates selected source capabilities, stages independent
job files, then releases CurrentSources guards/descriptors before returning opaque
Inputs with the original miss ticket. Consumer hits never acquire or stage those bytes.
Unavailable or changed sources return typed input refusals before child dispatch,
without rerunning an identity-known producer. The real Current/Frozen/CAS adapter is
still pending; fake test capabilities cannot become production StoredHit or group seals.
Final-demand accounting is separate from valid output identity: NotCached completion
can feed downstream staging but leaves an explicit Stored requirement unsatisfied.

Tests exercise mixed Checkout targets, Recorded/Current identity with unavailable
stores, conditional supported/unsupported/changed sources, dual explicit demands,
lookup/dispatch order, content cutoff, reference ordering, failures and cancellation.
A test-only BuildAdapter passes static fixtures through the real scheduler and the
unchanged independent A8 model plus clean oracle; an intentionally overbuilding adapter
is rejected. Reported staging/install/receipt counters do not certify native I/O.

Full `t0.output-cutoff` remains pending. Production A5/B7/C1 adapters, metadata-only
group key preparation, resident C5c lifecycle, A6 edits, dynamic cold targets, persisted
retirement and native materialization proof remain separate acceptance work. The
executor owns admission, sessions, retry, deadlines and cleanup. This slice resolves
identity closure before target lookup; it does not claim target-first cold discovery
or activate production v1.

Selected downstream source custody: `WriteTransaction::pin_recorded_items` checks/pins only requested
fixed item IDs from its same-store `RecordedIdentities`. `pinned_objects` exposes existing claims;
both return borrowed clone-only providers. `retain_recorded` roots checked metadata and releases its
read ticket without requiring payload availability or claiming Stored. Cached checkout plans may
opt into `commit_with_sources`, borrow `cached_sources` through downstream staging, then call
`finish_sources` (also when no consumer stages). Root success leaves these source claims active until
that explicit finish; failed finish/drop retains claims conservatively. Ordinary commit releases as
before. A committed local plan retains `local_completion` for frozen store-only siblings, without
opening CAS or converting Current into Stored. These accessors remain unused by production v1.

## Plain-Python data op (D1)

`py_data::PyDataSpec` converts unit-family input slot, output class and parameter schemas into a
validated `validate::OpDefinition` for `op = "py_data"` (version 1). Because `py_data` is a generic
host-data op, every content input slot, reference slot and parameter name must be declared explicitly;
allowed output classes are restricted to data classes (`data`, `json_data`, `route_data` and
`runtime_data`), rejecting mesh and material classes. `py_data_validator_identity` and
`py_data_worker_identity` bind `PY_DATA_VALIDATOR_VERSION = "atelier-py-data-validator-1"` and the
real `python_worker.py`/`python_job.py`/helper closure into A3 unit keys.

`py_data::validate_py_data_unit_outputs` validates already frozen `results::StagedSource` snapshots
(or pre-staged output files via `validate_py_data_outputs`) against the unit's `PreparedUnit`
contract before B2 publication. It checks validator identity, enforces required vs optional output
completeness and unexpected-file rejection, verifies that reported file digests and sizes match the
frozen bytes, and dispatches payload format validation strictly on the declared `OutputClass`
(`JsonData` semantic UTF-8 JSON object/array with finite numbers and no duplicate keys,
`RouteData` finite waypoints and monotone distances, `RuntimeData` `ATD1\x01` binary tables,
and non-empty `Data`).

## Static Python backend checkpoint (A9b1, unused)

`python_backend` implements the existing static scheduler's authority, conditional input staging,
and per-unit frozen publication/local installation using B2/B3/B7 and the D1 validator. Internal
Recorded identity, short-lived Current observation and explicit Stored/Checkout requirements stay
separate. `finish` ends retained source custody after all consumers have staged. Explicit named source
capture supplies complete descriptor observations; later live-edit acceptance remains A6 work.

`python_worker` binds exactly the frozen worker, job bootstrap and protocol files into its implementation
identity, then materializes those same files read-only under each unit's local lease. Installed Python
and dependencies remain platform context. `python_executor` uses one independent C5c session per
original miss ticket. The existing exclusive build guard is duplicated for the monitor only; actual
worker and correlated monitor identities must be durably added to both original leases before Run.
Normal unit limits remain 120 seconds of execution, 30 seconds of cleanup and 1800 seconds overall;
the session backstop is their checked execution-plus-cleanup sum (150 seconds). It does not reuse a
resident worker or accept quiescence in place of full guard cleanup. A crash retry that would need
fresh staging refuses before a second Run and preserves partial evidence. The scripted-bridge
constructor exists only in test builds. Portable synthetic guard tests verify this production path's
registration and settlement gates, not actual admission, sandbox execution or monitor cleanup.

This unused checkpoint includes real sandbox/I/O T1a cases and independent-harness integration.
Dynamic cold targets, conditional regeneration of unavailable recorded payloads,
cross-process retirement, A6 fencing, resident guarded batching and I1 caller activation remain pending.

## Cleanup policy facts (B5 first slice)

`cleanup::plan_catalog` analyzes caller-supplied metadata facts without filesystem access or a
mutation API. It validates every supplied reference, accounts for shared CAS payload bytes once,
protects roots/lease sets/recent or unknown observations and their producer closure, and proposes
oldest currently eligible result removals. A producer stays while a remaining consumer refers to
it. Cyclic closure is conservatively retained; missing producer metadata refuses a plan. Missing
payloads are reported as missing, without inventing availability or byte counts.

Age is a durable use/grace observation's conservative upper bound; payload mtime and production
provenance are not last use. Unknown and future observations retain. A single absolute deadline
covers all fact validation/planning and returns no partial plan on expiry. The explicit byte target
is a logical unique CAS budget; physical APFS space freed is unmeasured. Unresolved pre-publication
lease keys conservatively fence proposals, rather than being guessed to have no upstreams.

This pure plan is diagnostic, not filesystem snapshot/deletion authority. Raw metadata acquisition,
B4/B4b usage retention, the sole `roots::may_reclaim` adapter, same-store custody, actual unlink/fault
handling, the restore/GC race, CLI wiring and physical free-space proof remain separate. No shared
store cleanup or production activation is added. All nine registered pure cases remain T0; the
pending `t0.restore-gc-race` row is retained.

## Unreal worker (C3)

`unreal::UnrealContext` declares what one Unreal session loads: the engine root and BuildId, the
editor compile (`Binaries`: a produced folder and its `tree_identity`), the project modules, the
declared engine plugins (each with the `tree_identity` of its installed descriptor and `Binaries`;
default-enabled engine plugins are bound only by the BuildId), the project plugins (the editor-only
`AtelierBuildWorker` plugin is required)
and the declared `-ini:`/`-ForceDPCVars=` settings. `identity()` drops every location, and
`profile()` (`unreal-<sha256>`) is the scheduler's `Compatibility.profile`. The profile only groups
sessions: semantic ini, CVars and module bytes still enter each unit's key.

**DDC.** `UnrealDdc::open(store, build_id)` gives the context its derived-data cache folder,
`<store root>/unreal-ddc/<engine BuildId>`. The v2 store owns it. It outlives jobs and sessions, and
nothing cleans it per job. It is rebuildable acceleration only: no reuse, key or receipt decision
reads it, and store GC may drop it whole. Every session passes `-nowrite -NoZenAutoLaunch` and
`-DDC=(InstalledEnginePak,V2Local=(Type=FileSystem,Path=<folder>))`. Those flags, the graph and the
folder are in the profile, so changing any of them gives a new session. Before `hello` the worker
reads the editor's effective cache graph from the plugin and records it in `unreal-context.json`.
It refuses the session if the graph holds anything else:
- a Zen, shared, remote or unknown store;
- a file-system node outside the folder;
- a pak other than the installed engine pak.

It also refuses if no node is inside the folder. The controller checks the recorded graph again.
The graph cannot show a pak opened for writing, so the receipt stamps the installed engine pak and
`verify()` refuses any change to its size or modification time. That stamp is not a content hash and
does not prove the pak stayed read-only (a named gap). The T2 probe timings came from tiny inputs and are not
representative; real assets are measured after C3.

**Frozen worker.** `UnrealWorkerBundle::read(dir)` freezes the bytes of `unreal_worker.py` and the
`protocol.py` it loads when the context is declared. Each session writes them read-only to
`<session>/worker/`, and the editor runs that copy, so a later source edit never reaches a session.
`digest()` is their content identity. It is in the profile and exposed for the future D4/A9 item/op
key binder, which must also hash the compiled project module and plugin outputs and the semantic
settings, never the installed BuildId, editor or engine-plugin bytes, or DDC paths. The worker
reports the digest of the files it actually loaded before `hello`.

`ScratchProject::prepare(session, ctx)` builds `<session>/project/Atelier.uproject` with empty
`Content`, `Config`, `Saved` and `Intermediate`, and a session `user/` folder. It APFS-clones only the
editor binaries and each plugin's descriptor and `Binaries`, checks them against the declared
identities, writes `scratch-receipt.json` and `Atelier/expected-context.json`, and makes the clones
read-only. A module the editor wants to rebuild therefore fails closed. `verify()` rechecks the
receipt after the session. Off macOS, `prepare` refuses with "requires macOS".

`job_loop_command` runs `UnrealEditor-Cmd` on the scratch project with
`-run=pythonscript -script=platform/studio/atelier/build_v2/unreal_worker.py`, fixed unattended
flags, `-NullRHI`, `-nocrashreports`, `-UserDir=<session>/user`, the DDC flags and graph, and the
declared settings. The launcher appends the
protocol descriptors. Once per session, before `hello`, the worker:
- recomputes each declared engine plugin's identity from the folder the editor loaded it from;
- reads every declared setting back from the editor: a missing value never matches, ini values
  compare as exact text and CVars as exact text or the same finite decimal, and each raw readback
  is kept in `settings_read`;
- writes `<session>/unreal-context.json` (what the editor loaded and holds).

The controller reads that file with `verify_context_report()` before the first `Run`.
Each job then:
- gets an empty `/Game` with its input packages copied in read-only;
- must save exactly its declared packages, which move to `output/content/Game/`. Each collected
  file must hold the bytes its last save wrote, and every required output must exist. The plugin
  hashes the files a save wrote (its target, and each companion it created or replaced) with SHA1
  after flushing its writes; that hash is integrity only, never a key. A file already there that the
  save left alone fails the job. Each file keeps its latest attestation and the package that saved
  it: a file saved by two packages, or attested by another package's save, fails the job.
  A file written straight into `output/` fails the job;
- leaves each saved file's own import table in `evidence/imports.json` (`read_import_evidence`). An
  unreadable table fails the job.

After each job the worker resets Python state, `/Game` and the asset registry. It unloads the
touched packages with the plugin's synchronous garbage collection, in up to three passes, because an
imported package survives its first unload. Each package is then checked with `find_object`. Every
console variable that existed before the job must keep its value, and one registered during the job
must still be at its default. A failed ensure fails the job. If any reset check fails, the worker
replies, then exits.

The editor-only plugin lives at `unreal/AtelierBuildWorker`, outside every folder a game or v1
enumerates. It is cloned only into scratch and micro projects, and its compiled binaries are never
committed. Its library is the editor surface the worker uses:
- native context;
- the effective DDC graph;
- save recording with flushed file hashes;
- each saved file's import table;
- ini values;
- ensure counting;
- dirty and loaded packages;
- the CVar snapshot;
- synchronous GC;
- registry forgetting;
- diagnostic reference chains.

T0 runs this end to end against `tests/fixtures/fake_unreal.py`, a stand-in editor with the same
command line and plugin surface. Real-editor behaviour (descriptor inheritance, `-UserDir`, shader
workers, registry forgetting and engine-wide writes) is T2 evidence. Unreal is not sandboxed.
The engine-wide writes the T2 probes measured are named proof gaps in `build-v2-unreal-scratch-project`:
- EditorSettings.ini (stopped by `-nowrite`);
- the tool preset JSON;
- `Trace.uba`;
- Zen files and its status utility;
- crash reports;
- the shared filesystem DDC, which a session refused for its graph may already have written at startup.

D2 unused Blender op definitions and in-job bodies support the initial schema-2 MeshIR → FBX route. See [Blender op contracts](../../docs/build-v2/BLENDER_OPS.md) for ownership, frozen validation and pending native acceptance.

Failed Python targets retain bounded, attempt-specific diagnostics privately in the original
leased guard parent as `diagnostic.json`. The normal CLI prints the private controller-log
locator; that log points to the diagnostic file, or reports a retention error. Read each
attempt's `source`, optional worker `kind`, `message` and `truncated` flag. A missing message
means the cause is unknown. These records do not certify cleanup or cache publication and are
not included in public CI artifacts or semantic keys. Successful `Completed` observations do
not create this failure file. The first M1 failed call predates this retention and its cause
remains unknown; no retry or default mixed-build activation follows from this diagnostic API.

The Python sandbox permits the installed platform's OpenSSL configuration through the single
canonical read literal `/private/etc/ssl/openssl.cnf`, as it permits installed interpreter files.
The worker source change updates its semantic bundle identity normally. The installed config
contents remain platform context, not a new game input or automatic installed-tool key. Neighboring
certificates/hosts, directory data reads, Mach lookups and network access gain no permission;
no `OPENSSL_CONF` override skips configuration. Profile-only portable tests inspect this boundary;
they do not prove successful Mac execution. Both stopped M1 attempts have independent later OS
reports binding their child to its guarded parent and recording that exact denied config read.
Original receipts remain unchanged, and neither op-body progress nor a successful build is claimed.

fencing and private same-scope repair demands. It has no production plan issuer, caller, repair CLI
or bootstrap; it does not activate mixed/default builds or qualify arbitrary legacy/native work.

The continuous legacy authority-parent implementation is described in
