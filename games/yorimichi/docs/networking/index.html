01 / INTENT

Two players first. Multiplayer by design.

Begin with your game hosting while your brother connects through Tailscale. Build the same gameplay authority to run on a central server, with configurable capacity and more players later.

Explore

Arrive beside you.

Join in progress, see each other on the map, walk, sprint, double jump, climb, glide and swim with the merged moveset. “Meet up” brings a consenting guest to a safe point nearby.

Skate

Keep the board’s feel.

Each machine runs its rider’s existing board physics. The other player sees a smooth stream of the actual rider and board pose, including tricks, bails and getting up.

Fight

One agreed outcome.

The host runs enemies and decides damage, guard, parry and knockdown. Both can fight shared enemies; consensual sparring uses the same merged moveset.

The central choice: use Unreal’s normal replication and predicted character movement on foot; delegate skateboard simulation to its owner for this trusted two-person session. Keep combat decisions on the host. This contains the hardest physics problem while preserving the experience you want. Two is the first tested session size, not a limit in the player, encounter or vehicle data model.

Intended multiplayer scope: touring, skating and merged-moveset combat, followed by riding bikes together, sailing alongside each other and sharing a zeppelin journey. Central hosting and larger sessions are explicit roadmap goals. The first playable slice proves tour/skate/combat; it keeps vehicle interactions gated until their multiplayer adaptation passes. Horses and races remain separate future work.

Initial boundaries: no physical collisions between players or between their personal rides, no mounted attacks, no public matchmaking and no listen-host migration. These are scoped first-release choices. Offline play keeps its current features.

Assumptions pending your preferences: both cooperative fights and friendly sparring; Mac-to-Mac is the first proven packaging path. Your brother’s operating system and hardware still need confirmation. If he uses Windows, the Windows package becomes an early delivery gate.

Move locally; reconcile with the host.

The guest predicts movement immediately and sends saved input to the host. The host reproduces it and corrects disagreement. Other characters interpolate the authoritative state. Custom traversal needs its own saved state; existing Unreal walking support does not automatically cover the merged moveset.

Simulate once; show the result remotely.

The rider’s machine owns native skating and its Chaos bail body. It sends bounded pose snapshots to the host, which validates and relays them. Remote copies run presentation only: no second native session, no remote ragdoll physics, and no duplicate board input.

Predict the action; confirm the consequence.

A button starts a local predicted action. The host validates the move, resources, range, defence windows and targets, then publishes an identified outcome. Health and knockback are committed once, together with the reaction state. The host uses the same action rules for its own player.

Unreal responsibilities and wire contract

GameInstance handles travel and failure recovery. Server-only GameMode admits players and owns spawn/encounter rules. GameState publishes session configuration, world identity and server time. PlayerState publishes stable identity, appearance and readiness. The owned PlayerController carries join/readiness and interaction requests; each replicated Character carries its movement/action state. A world bootstrap builds gameplay collision/data on the server and each client; rendering, UI and ambience run only on clients. Capacity is configuration, initially two. Player, encounter and vehicle collections use stable IDs and generations, never fixed host/guest fields or player index 0.

Use bounded reliable RPCs for admission, invitations and activity transitions; movement and pose traffic are unreliable and sequenced. Repeated held-input state and explicit release/timeout prevent a lost release from sticking. Keep causally linked move/action fields together, identify outcomes, and apply snapshots idempotently. Never rely on property/RPC ordering across actors. Unknown pawn, appearance or board generations wait for their baseline or are discarded, never applied to the wrong character.

After content validation, the guest reports completed local world/collision/rail readiness. The host sends current player, board, encounter and shared-actor baselines; the guest acknowledges that baseline revision before possession/input. Start with a fresh nearby spawn on rejoin. Replicated state restores late join; one-off multicast events do not.

02B / HORIZON

A server without a host player.
A world with more friends.

Central hosting is part of the destination. Establish the boundaries now so a two-player prototype can grow without rewriting who owns the game.

First / listen server

Invite your brother.

Your machine runs gameplay authority and your local view. Two is the initial capacity setting. The session ends when you close the host.

Next / dedicated server

Meet at a shared address.

A headless Unreal process runs the same world, combat and vehicle authority. Everyone connects as a client. The world can keep running when any player leaves.

Later / many instances

Grow beyond one machine.

A session service directs groups to available world instances. Each instance has a tested capacity; more instances serve more people. Friends deliberately join the same instance.

What “any number of players” means architecturally: no fixed two-player assumptions, configurable session capacity and a path to scale across servers. One simulation still has finite CPU, memory and bandwidth. An arbitrarily large crowd in one seamless world would require a separate distributed-world design, including authority transfer between regions; adding servers alone does not make that work.

Make these choices before the first multiplayer build

Send each player what they need to see

Use spatial interest plus explicit encounter and vehicle dependencies. Nearby skaters receive detailed poses; distant riders receive reduced-rate roots/action state or a cheaper pose representation. Combat participants get the state required to resolve and display their encounter.

03 / FEEL

Protect local responsiveness.

The player should feel their own input immediately. The hard work is keeping the remote view and the next activity consistent.

On foot / authoritative prediction

Make custom moves replayable.

Extend Unreal’s saved moves and packed move data. Define a replayable moveset state object, rather than a short hand-picked list of flags. Save/restore glide speed/yaw/turn; drive origin/scale/basis and previous path time; hop velocity; flip time; grounded/jumped state; jump buffer; climb lockout; push timers; invulnerability/perfect-dodge windows; stamina; action ID/phase; climb anchor; and transition epoch. Audit every mutable simulation field. Full prediction snapshots stay local; serialize the inputs and authoritative correction state actually needed.

Transmit quantized raw stick intent, facing, walk/jog/sprint holds and sequenced button edges in saved move data: acceleration alone is insufficient while a move locks locomotion. Process Press, jumps and mode switches inside that step, not directly in input callbacks. Move gameplay advancement into the movement simulation step so a correction replays the same action clock and movement. Separate replayable state from sound, particles, damage and one-shot animation events; replay must not apply them twice. Landing/plunge and fall damage are host-only; predicted stamina rolls back with the saved move. Replicate an explicit traversal submode because glide, climb and swim currently share custom mode 3; simulated proxies never advance the moveset gameplay clock. Root paths become movement-component operations or suitable root-motion sources, not independent actor Tick teleports.

Every custom traversal mode needs a host-validated start and replay state: ledge fit, climb surface, glider opening and water state. Preserve collision sweeps and fit rules. Locally generated static surfaces need stable authored IDs plus anchors; do not send raw pointers or assume independently generated components share network identities. A failed mode is a failing tour gate, not permission to quietly remove a merged move.

Epic’s movement extension points
Skate / trusted owner simulation

Send what the rider actually did.

Capture after animation and physics from the skeletal mesh: its world transform and component-space bones. Actor root plus RetailPose misses the physical bail pose, capsule resize, mesh offsets and get-up clearance. Clip names alone cannot reproduce procedural balance or a Chaos fall.

A proposed snapshot carries protocol, pawn generation, activity epoch, sequence, time, root transform/velocity, stance, board state, pose blend, compressed component-space bone transforms and schema-defined board-part transforms. During bail/get-up, test a compact stream of roughly 17 physical-body world transforms plus recovery state, reconstructing presentation without running remote physics. The pose schema and character proportions are hashed; non-finite, oversized, stale or out-of-bounds data is rejected.

Start ordinary riding at 20 snapshots/second, with independent samples and roughly 100 ms of remote interpolation. Test 30–60 Hz for the smaller bail/get-up body stream; interpolated falls must pass the same skin-clearance gate as local falls. Apply a presentation-only static-ground clearance lift where necessary. Cap extrapolation at 100 ms, then hold/fade with a connection warning. A later full sample repairs loss. Do not replay remote physics or apply another smoothing layer to the same root.

This is deliberately trusted movement, not an anti-cheat guarantee. No player–player physical contacts, shared competitive score authority, or damage while riding in v1.

The most important integration rule: one movement driver at a time. Keep the pawn replicated, but explicitly gate ordinary CharacterMovement input, correction and proxy movement while the skateboard snapshot driver owns it. A server-accepted activity epoch switches all copies together. Do not simply turn off actor replication or globally accept client positions.

Mounting, bailing and coming back to combat

The owner requests a transition with a unique ID; the host accepts a new epoch and publishes the starting transform, velocity and activity. Cover all three exits: dismount, bail get-up and Native BipedGround takeover (including its carried velocity). A Ride clip finishing also changes the movement epoch. The final skate snapshot seeds dismount; the host checks placement, restores CharacterMovement and acknowledges the on-foot baseline before combat becomes eligible. Reject old-epoch snapshots and saved moves. Mount denial resets to the accepted state. The handoff includes restored capsule dimensions, step height, mesh offset and mesh-settle phase. Validate dismount with the restored on-foot capsule. Keep bail recovery, carrying the board, loose-board recall and jumping out of a carry animation inside the same transition contract. Teleports and character swaps also create new generations/epochs and flush interpolation and prediction history.

The board has a life of its own: give it a separate owner stream and generation, continuing while the rider is on foot. Replicate its place (hand, riding, lying or away), world transform, visibility/dissolve alpha and settle state; reduce updates once it rests. A rider movement-epoch change must not freeze a loose board. Reattach only against a known rider/character generation, and expire it on disconnect. Send identified disposable land/grind/bail cues plus durable speed/surface loop parameters so the remote skater is audible.

No hidden remote collision: remote skate copies create no Native session, physical rider or collision-enabled board. Explicitly exclude other players and remote boards from ground-clearance, deck-fit, mount and get-up queries and Native static-world capture. Retain a separate combat-query path for on-foot targets; “ignore physical collision” must not make opponents unhittable.

Joining during a bail: send the current activity, absolute pose, independent board baseline, get-up blend and mesh-settle state, not a “start bail” event. A remote presentation path must display this baseline without starting Native or Chaos. Restore only the locally owned simulation when reconnecting; initially respawn at a server-approved party anchor or safe spawn rather than attempting live physics-session restoration. A dedicated session has no special host avatar.

04 / COMBAT

Share the fight, keep the rules.

Preserve the merged moveset’s actions and defence logic. Separate authoritative combat time from the visual effects that make a hit feel good.

Cooperative encounters

Host-only AI selects from all eligible players using range/threat and explicit encounter membership. Skating and the later vehicle slice belong to peaceful touring initially; joining a fight requires an acknowledged on-foot state, and mounting/travel is denied while an encounter holds the player. Replicate enemies once, including health, target, action and recovery. All admitted participants can damage the same enemy; friendly fire is off by default. A server encounter director owns spawning/reset, per-encounter threat and nearest-eligible targeting, leash rules and a cap on simultaneous attackers. Tune encounter difficulty explicitly for participant count; late join does not reset health or retroactively rescale committed damage. Keep damage deduplication per attacker, action and victim.

Hunter and creature target selection must stop assuming player index 0. Kaede’s existing duel stays one participant at a time; other players can watch. A two-person trainer encounter would be separate behaviour, not an accidental second opponent.

Friendly sparring

Invite, accept, safe reset, then begin a host-owned duel. Both players use the merged move data and the same stamina, guard, stagger and knockdown rules. Replicate each player’s shield/equipment and moveset selection; hashing shared assets does not communicate personal choices. The initial online mode selects merged for all players. Combat ends on defeat, cancellation, disconnect or leaving the agreed area; restore the agreed practice health.

Generalize IsSparringWith into host-owned encounter/team rules instead of identifying Kaede’s class. Non-participants cannot damage the bout. The winner is a casual result, not a competitive fairness promise.

A single combat timeline

  1. Input: send an identified action and input edge, facing/target request, movement epoch and timestamp tied to the accepted movement stream. Bound rates and release held inputs on focus loss or stale input.
  2. Prediction: play the local action immediately. The host checks action legality, movement mode, timing, charge, stamina and target. An accepted action gets a canonical start time/phase/rate and serial. Latch homing target ID and target position/drive direction at action start; any later retarget is an explicit authoritative update. Never aim replay at an independently moving live target. Rejection reconciles the owner without duplicating effects.
  3. Resolution: the host evaluates authored active windows and collision sweeps once, at a defined tick order after movement. Server bone/weapon transforms must update even when offscreen; do not rely on a remote client’s mesh trace or render rate.
  4. Outcome: replicate durable health/action state and an event ID for hit, guard, parry, dodge or knockdown. Apply knockdown/recoil as one epoch-stamped outcome containing reaction, authoritative movement impulse and action phase; a bare position correction would leave the owner replaying the wrong move. Use absolute state for late join; transient sparks and sound are disposable. Local predicted effects reconcile by ID. Camera shake and damage flash route to the affected locally controlled player, never an unconditional pawn-0 call on the host.

Latency policy: start with host-authoritative hit geometry at its current simulation time. Add a small, bounded defence grace window as a measured option: retain the recent accepted defence inputs, hold a candidate hit briefly, resolve it once, then commit health/reactions. Clamp client times to measured connection timing and reject future, expired or replayed input. A provisional 50–100 ms bound needs tests against the existing 250 ms perfect-dodge window and both players’ visible attack timing; it is not full rewind and cannot make a distant opponent’s displayed position current. Apply the same rule to host and guest. Do not finalize damage and later resurrect it as a parry.

If 80–150 ms RTT sparring cannot meet the acceptance tests, the next design step is bounded historical hitbox/defence evaluation, with a shared time convention and simultaneous-hit rules. Do not hide a failed combat gate behind a good LAN demo or silently switch to client-reported hits.

Flurry rush must change its treatment of time online. Keep perfect dodge and its follow-up opportunity, with a host-timed action window. Use a bounded target recovery/stagger state for enemies and an explicit agreed duel reaction for a sparring opponent. Keep camera emphasis, trails and sparks local. No global world slowdown and no actor time dilation on network movement. Visual hit-stop freezes/blends presentation only; gameplay windows use authoritative time. This is an intentional multiplayer tuning difference that needs playtesting. During P3 development, keep sparring flurry disabled until measured; the complete merged-moveset release must pass the adapted flurry gate or clearly remain incomplete.

The current trainer already performs a flurry without slowing the player’s world, but its code is not yet a complete online solution. Its !IsPlayerControlled() check does not select a listen-server guest, and its invulnerability is assigned before a duration cap. Online code must explicitly select the network policy and compute capped action/invulnerability durations together. Reuse the idea, then audit all SlowMotion, HitStop, FApp::GetDeltaTime and CustomTimeDilation paths. Limit repeated flurry/stagger so two players cannot permanently lock an enemy.

04B / RIDES

Bike together. Sail together.
Take the same zeppelin.

These are planned multiplayer features. The current implementations contain local control and camera assumptions; each gets an explicit movement, occupancy and recovery contract.

One shared vehicle, one authority: assign a durable vehicle ID/generation, seat slots, occupant IDs and a server-granted control lease. Send requests through the requesting player’s owned controller; validate range, activity, seat availability and world readiness before reserving a seat atomically. A control lease is gameplay permission, not permission for every passenger to send RPCs on the vehicle actor. Driver changes and boarding/dismounts advance epochs and reject old input.

Bikes / personal rides

Pedal side by side.

Use server-authoritative movement with rider prediction. The bike already uses walking collision, but its speed, steering, crash checks and clip clock advance in component Tick. Move gameplay advancement into replayable movement steps; save the full state needed for correction, including sprint/coast, recoil and mounting phases.

Replicate clip/phase and procedural parameters for steering, pedals, lean and ground fit. Separate collision decisions from cosmetic audio/IK. Represent each bike as a separate replicated entity with an explicit owner and parked lifetime, rather than leaving its only state on the rider component. Give a parked bike its own durable transform so it remains visible after dismount or relevancy changes.

Preserve the current Cairo-compatible skeleton restriction until other riding animations are authored. One rider per bike initially; no bike-to-player ramming or mounted combat.

Bike implementation
Sailing / authoritative hull

Explore the coast together.

First support individual dinghies sailing alongside each other. Today the hull is a component of one rider: it directly moves that character and zeroes CharacterMovement velocity. Implement the initial single-rider boat motion as a replayable CharacterMovement custom submode, preserving sail target, speed, steering and hull/rider offsets in saved/correction state, with driver prediction and server correction; other clients interpolate the accepted hull state.

The server owns launch clearance, hull sweeps, shore eligibility and safe landings. Replicate sail/steering state and the phase needed for matching rider placement. Foam, wakes and cloth stay visual. Current propulsion follows the sail target; wind affects the boom’s appearance, not a full wind-driven physics model.

A shared passenger dinghy additionally needs authored seats, rider poses and safe hull capacity. The vehicle contract allows it, but today’s one-person asset is not silently treated as a two-seat boat.

Sailing implementation
Zeppelin / shared service

Board the same flight.

Run one server-owned route service. Replace the single Passenger, walk path and stored camera with per-passenger records, boarding slots and local camera state. Reserve places while docked, finish boarding before departure, then move all riders relative to the same smoothed ship frame.

Replicate route, dock/destination, phase, server time and flight-speed revisions; send a current baseline to someone joining mid-flight. The server owns gate/gangway collision and safe disembarkation. Initial riders use assigned positions; free walking on a moving deck needs a separate movement-base proof.

A current passenger can pause the ship through a menu, skip a flight or reset it through Cancel. Those single-player semantics must change before sharing a flight.

Zeppelin implementation

Agree on the journey, recover each person safely

Zeppelin controls: a server-issued route-controller lease lets one occupant choose the destination while docked and request flight-speed changes. Departure follows a visible boarding deadline/readiness rule; an unready reservation expires safely, never strands someone on a moving gangway. Skip requires consent from all current passengers and still executes docking/disembarkation. Dock calls use the same server lease and a bounded request queue; a caller cannot teleport an occupied or reserved ship away from another group. Before departure, ask unreserved bystanders on the hull/gangway to board or step off, or cancel departure safely. The current hull loses collision after the docked phase, so a bystander cannot simply be left standing on it. Opening menus changes only that player’s input/camera. If the controller leaves, elect another occupant or complete the current route automatically; releasing one passenger never resets the ship for everyone.

Movement handoff: extend the same single-driver activity epoch used by skating to bikes, boats and passengers. The server grants an accepted start frame, collision/movement mode and occupancy revision. Passengers have normal movement prediction disabled during server-driven boarding and flight. Give each passenger an attachment-backed assigned frame plus an authoritative boarding/disembark path and progress revision; client camera changes follow local state notifications, never server viewport calls. A passenger follows its vehicle frame exactly once; do not smooth a world-space rider independently and also add ship movement. A dismount validates a non-overlapping capsule placement, restores on-foot dimensions/movement and acknowledges the new baseline before combat becomes eligible.

Disconnect and conflicting requests: leases expire and held inputs time out. For a boat, stop propulsion and keep any remaining passengers attached until a safe exit or control transfer; for a zeppelin, continue to a safe dock. Phone/marker travel removes only that passenger through a validated safe transition; it must not call today’s global ship-resetting Cancel. Removing an occupant cannot destroy an occupied shared vehicle. Personal abandoned rides get a bounded cleanup policy after occupants are clear. A reconnect gets fresh state and a safe spawn. Seat reservations, route commands and changes of driver are idempotent and server-ordered, with denial messages only on the requesting client.

Vehicle proof: test both roles and dedicated mode, simultaneous mount/boarding requests, different character dimensions, crash/park/remount, boat shallows and blocked landings, menu/focus loss, driver disconnect, command conflicts, late join during boarding/flight, and passengers leaving independently. Repeat at 80 ms RTT/1% loss and stressed networks. Nobody is left swimming in air, duplicated on a seat, paused by another person’s menu or trapped in a vehicle movement mode. Boats and bikes initially ignore player/personal-vehicle physical contact while retaining authoritative static-world checks; shared ship/dock collision is synchronized.

Apply proportions/definition before movement and pose baselines; reject changes during a fight.

Platform-specific package SHA values may differ; the shared gameplay identity must match. Keep Unreal’s own compatibility checks. Host-owned session policy determines effective difficulty/physics tuning; local graphics and controls may vary only where gameplay is unchanged.

06 / DELIVERY PLAN

Build in playable slices.

Prove the riskiest assumptions first. The first evening together is a touring-and-skating milestone; the core release also passes combat. Shared vehicles and central hosting are explicit following milestones, with headless compatibility checked up front.

P0
Core spike · rough effort 2–4 engineering days, excluding D0

Two packaged players in the same world

Confirm the brother’s platform. Design for configurable capacity and complete the early headless spike below. Add host/join lifecycle, per-machine static bootstrap, classified dynamic/cosmetic spawning, authority-gated AI, per-player identity, local-only menus/settings and ordinary walking. Apply the online-capability gate to activities awaiting their vehicle slice from every input path. Verify the actual network permissions and Tailscale path.

Exit: two physical machines join extracted packages, see two independently controlled characters and disconnect cleanly. Reject a mismatched build. Record host CPU/memory before expanding scope.

P1
Skate feasibility · rough effort 3–6 days

Prove remote pose and movement handoff

Implement presentation-only remote skating and an initial absolute pose codec. Cover riding, trick, bail, get-up, carry, recall and dismount. Establish the single-driver epoch contract before integrating combat.

Exit: one uninterrupted ten-minute shared skate route at 80 ms RTT / 1% loss, including both stances and recovery; no competing simulation, repeated snapping or frozen remote rider. Include three bails per stance, on-foot and on-board get-ups, lying-board dissolve/recall and bailing beside the other player. Measure remote skin penetration (target ≤2 cm), packet sizes and traffic.

P2
Full tour · rough effort 4–8 days

Network the merged traversal and meet-up flow

Make sprint, double jump, climb, ledge transitions, glider and swim replayable. Add identity/equipment, map presence and safe teleport requests. Audit settings, character changes and unsupported activities.

Exit: a packaged tour through town and parks with all listed traversal, join while the host is far away, late join during skating, reconnect, marker travel and character switch. Offline regression checks still pass.

P3
Combat · rough effort 5–10 days

Shared enemies and consensual sparring

Separate gameplay and FX, host AI/health, action prediction, defence adjudication and durable outcomes. Adapt flurry rush and hit-stop. Prove cooperative enemies first and consensual sparring last. Validate every merged attack family and both defensive equipment choices.

Exit: cooperative and sparring bouts at 0/80/150 ms RTT, host roles exchanged, including simultaneous hits, parry, perfect dodge, charge, combo, guard break and knockdown. No health divergence, duplicate hits, stuck reaction/correction loops or excessive perfect-dodge invulnerability.

P4
Release hardening · rough effort 3–6 days

Send the build, then use that download

Exercise poor networks, suspend/reconnect, held-input timeout, clean-machine installation and a long real-distance session. Publish exact artifacts and validation receipts. Test both requested OSes if different.

Exit: you and your brother can complete a 30–60 minute tour, skate and fight session using only the distributed build and join instructions.

This is a code-audit estimate, not a commitment or benchmark. Re-estimate after P0 and P1; this estimate excludes the added headless/toolchain spike, vehicle milestones and capacity/hosting work below. Re-estimate those after their feasibility gates. 07 / CHALLENGE

Peer design review.

Four existing board agents challenged the initial design against their parts of the game. Their findings changed the proposal below. These reviews validate the plan’s reasoning, not an implemented multiplayer build. A second review round challenged the central-hosting, larger-session and vehicle extension. Its findings are incorporated too; no multiplayer implementation is claimed.

megapark · Skate / Ride · board #3334

The rider pose and the loose board are separate problems.

Changed the capture contract to post-physics mesh/component space, added a compact higher-rate bail stream as a feasibility test, gave loose boards independent lifetime/state, and specified remote collision-query exclusions. The exit gate now includes three bails per stance, both recovery paths, board dissolve/recall and a ≤2 cm skin-penetration target.

move-sets · Traversal / combat · board #3354

Network the input and the entire replayable moveset.

Expanded saved state and raw input beyond acceleration, moved action edges into movement simulation, made traversal submodes explicit, latched homing targets, and added epoch-stamped reactions. Included the third Native-to-foot exit and the existing flurry invulnerability-cap problem. Cooperative combat precedes sparring; flurry remains a measured final-release gate. The reviewer confirmed all nine findings addressed, with no further design objections (board #3360).

hidamari · World / local presentation · board #3351

A copy of the world loader would duplicate gameplay.

Added a spawn-category table, host-only AI decisions, fixed online zeppelin/race-gate state, per-player character identity and local-only menus/settings. Added one activity-capability gate across input routes, safe live-bridge restrictions and the alternate map-mode boundary. Cosmetic residents remain local.

jim-playtest-01a107d7 · Release / packaged QA · board #3342

Make the proof come from the distributed builds.

Corrected the entitlement assumption: r4 already carries client/server capabilities. Added reciprocal sharing for exchanged host roles, actual-content compatibility, startup-crash distinction, native packaged diagnostics and a receipt for both artifacts. Clarified that developer QA guards are separately provisioned, not included in the brother’s install flow.

Extension review · board #3408, #3417, #3426, #3427, #3431

Headless data and shared vehicles need their own proof.

Added a separate server artifact/data contract, cooked-collision parity checks, headless attack-pose evaluation and crowd/bail budgets. Source inspection confirmed the existing Chaos surface fallback, correcting an initial claim that server skating would necessarily have no collision; the skate reviewer agreed. The remaining issue is retention and parity in an actual server cook. Added bike entity lifetime, sail custom-mode replay, queued zeppelin calls, dock bystander safety, passenger prediction/attachment rules and independent passenger cancellation. Core bootstrap, encounter targeting and presentation-only combat FX remain prerequisites.

Still to establish through implementation: pose bandwidth and bail clearance, complete movement replay, server frame budget, guest parry/flurry feel, headless packaging, shared vehicle transitions and clean-device networking. The brother’s OS/hardware remains an open product input. None of these are claimed solved by a static design review.
