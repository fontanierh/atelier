## How the boundary is found

A radius cannot separate the stalls: `procedural/market.py` jitters each stall with the shared `RNG` and the clutter
(parasols, carts, trees) lies between them. So the tool replays the donor's owning constructor in pure Python:

1. imports the donor `market()` / `lower_town()` / `upper_town()` and seeds `RNG` at the exact stream position the donor
   export used (`assets/brinecove/export-parameters/<Component>.json`, `positioned(seed, prefix_words)`);
2. wraps `Builder.face` and, for every face, walks to the constructor's frame; a face made inside the body of a stall loop
   (stall, its barrel and crate) or of a building-lot loop (foundation, stilts, ladders and all the houses `split_lot` cuts
   the lot into) is that object's; everything else is nobody's. Loop bodies are found by header text with `ast`, so a
   renamed loop fails loudly;
3. matches every generated face to the donor GLB triangles by the float32 vertex positions (`(x, y, z) -> (x, z, -y)`,
   any triangulation of a quad). The match is exact: 405,778 of 405,778 triangles of the 28 market tiles, and all town
   tiles, are found, none is generated by two objects, none is left unmatched (otherwise the tool refuses).

Nothing in the donor is modified. Earlier batches (every other `split-*.json` in the region folder, batch 1's radius cuts
included) are subtracted first; a triangle that belongs to a stall but was already taken by an earlier batch is an error
(none in the recorded plan: the well and auction block took no stall triangles).

Objects: 21 stalls (`market-stall-01..19` in `L.MARKET_STALLS` order, and the two south-edge stalls
`market-stall-south-west/east`), and one object per dense lot of the lower and upper town, named `town-lower-<key>` and
`town-upper-<key>` after the layout key. `brinecove_market.py list --donor D --components Market,TownLower,TownUpper`
prints every object with its triangles per tile.

## Ownership after a batch

Same as batch 1. Each part becomes `prop/brinecove/<object>` (`-soft` for a part cut from a Soft tile; no collision),
with render, collision and LOD settings copied from the tile. A surviving tile record retains its full pinned donor GLB
and a pinned carve selection; the derived remainder has its own triangle count and slot list. The source GLB is not
overwritten with that remainder. A new `object/brinecove/<object>` placement (identity transform, same flags as the
tile) is added to `objects.toml`; the existing `object/brinecove/market-3-4`, `market-4-4`, `market-3-3`, `market-4-3`
and `townlower-*` placements keep their groups and now draw the remainders.

The source-preservation conversion ran after town9 ([sources.md](sources.md)): full originals and carve selections
replace in-place source mutation, and no accepted package was re-imported.

## Controller sequence

Choose an unfinished named batch from the current plan; `market1`–`market3`, `town1`–`town9` and `props1` below are
completed evidence, not a work queue. Replace the placeholders with the selected batch, its changed record IDs and
its object IDs.

Size the import queue to the prepared, dependency-ready set of one asset kind, within the session's memory ceiling and
deadline. The former `--batch 8` example was not a limit: `props1` had 26 static-mesh records that could share one
headless queue. The caller still splits kinds and dependency boundaries, checks each job's claim and saves, and
preserves completed work for retry. Keep one controller for shared packages; do not change code during its session.

```

V2_SPLIT_BATCH=UNFINISHED_BATCH_NAME
V2_IMPORT_BATCH_SIZE=READY_RECORD_COUNT

bc_market plan  --batch "$V2_SPLIT_BATCH" --donor "$D"  # parts, remainders, tile arithmetic
bc_market paths --batch "$V2_SPLIT_BATCH" --donor "$D"  # claim exactly the 'apply' list (--json for the scopes)
bc_market apply --batch "$V2_SPLIT_BATCH" --donor "$D" --claim TASK
# Use the explicit changed record IDs from this batch plan.
uv run python games/yorimichi_v2/tools/import/run.py ID... --claim TASK --batch "$V2_IMPORT_BATCH_SIZE"
# Repeat --only once for each object ID from the batch plan.
uv run python games/yorimichi_v2/tools/migrate/objects.py region/w09-brinecove --environment region/w00-island --claim TASK --only OBJECT_ID_1 --only OBJECT_ID_2
bc_market check --batch "$V2_SPLIT_BATCH" --donor "$D"  # counts, bounds, drawn once, and donor tile = parts + remainder + earlier parts
uv run python games/yorimichi_v2/tools/content/check.py
```

difference for tiles a later batch has cut further (`Market_4_4_Piece003` after `market1`, `Market_4_4_Soft` after `market2`). Run it before applying
the next batch; the newer batch's `check` is the proof for those tiles.

### Emptied tiles: retire in three stages

A town tile is often made only of lots, so a batch can take every triangle (no remainder). `apply` leaves such a tile's
record, package and runtime group in place and `apply` never deletes, so until it is retired the old tile and the new parts
are both drawn. After accepted imports and `check`, retire them under the same complete claim, in this order:

1. `groups`: drops the emptied tiles' groups from objects.toml, objects.saved.json and the runtime file, and their
   records from each placement's model list (otherwise the re-saved placement still references them).
2. `placements`: deletes each affected placement's record folder and the actor packages it lists as outputs. It refuses
   unless the groups stage is done and the check passes, and it prints the placement IDs to save again. A saved object
   cannot change its groups, so these actors must be saved again.
3. `records` (after the placements were saved again): deletes the emptied tile records and package files.

The stages take `--batch all` (every market, town and props batch, in apply order) or a comma list. Each stage runs its batches
in turn, and the placements stage deletes each placement once for the union, so the same actors are not re-saved per batch.
Batches with nothing emptied are skipped. The placements are found from their records as well as from objects.toml,
because the groups stage removes the groups from objects.toml but not from a record. A rerun of the placements stage finds
nothing to delete; keep the list the first run printed.

```
D=DONOR_BUILD_DIR
TASK=claim-task-id
bc_market() { uv run python games/yorimichi_v2/tools/migrate/brinecove_market.py "$@"; }
bc_market paths --batch all --donor "$D" --json                       # the union of paths, scopes and placements (read-only)
bc_market retire --batch all --donor "$D" --claim "$TASK" --retire-stage groups
bc_market retire --batch all --donor "$D" --claim "$TASK" --retire-stage placements   # prints the placement IDs to save again
uv run python games/yorimichi_v2/tools/migrate/objects.py region/w09-brinecove --environment region/w00-island --claim "$TASK" --only OBJECT_ID_1 --only OBJECT_ID_2
bc_market retire --batch all --donor "$D" --claim "$TASK" --retire-stage records
bc_market check --batch all --donor "$D" --retired
```

The single-batch form (`--batch townN`) runs the same three stages for one batch; the placements of a single batch are
deleted in that batch's own pass. For a batch set that shares a placement, use `all` (or the list) so it is deleted once.

Before applying a batch, the claim base must match the accepted integration base and cover every touched package
and companion. A stale claim is repaired with completed work preserved; it is not a reason to repeat accepted imports.
Retirements use the authorized journal path/scope set and refuse unrelated or stale ownership.

## Cargo re-split (`props5`)

`props5` splits two kinds of accepted coarse objects into their pieces, one per `crate(...)`, `barrel(...)` or
`b.ring(...)` call:
- each of the six `props2` quay cargo clusters into its two crates, two barrels and rope coil,
  `props-cargo-<side><|x|>-{crate1,crate2,barrel1,barrel2,rope}` (36, 128, 144 triangles);
- the cargo on each `harbor1` pier: a crate and a barrel at 22, 52 and 78 % of its length and a rope coil at 52 and
  78 %, `harbor-pier-<pier>-{crate,barrel,rope}<t>`.

`REPLACES` names the coarse objects. `plan` takes a replaced earlier object's triangles out of the tile as before,
except those of this batch's pieces inside it, so the tile remainders do not change. Each coarse record then loses
exactly its pieces' triangles (every piece triangle must match exactly one of the record's, by its welded corners):
- a cargo cluster keeps nothing and retires like an emptied tile: its group (`retire --retire-stage groups`), its
  placement (`placements`, nothing is saved again because the object is gone) and its record (`records`);
- a pier keeps its deck, piles, braces, bollards and lanterns and is carved like the shipyard yard. Its pinned original
  stays the first source, `src/<mesh>.carve.json` the second, and `[derive]` names both. `apply` writes the carve with
  the pieces, so the one import takes both.

The expectation's `replaced` section records each re-cut (before, removed ordinals, pieces, the derived mesh's hash and
triangles). `check` proves each carve through its derivation and that it holds no piece triangle. The `props2` and
`harbor1` checks drop only the problems the re-split explains (a retired record, its missing group, a carved count). The
donor proof counts the later pieces in place of a retired coarse part.
